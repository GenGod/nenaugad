## 2. Что значит «API» в рамках ADR-001

**Проверенный факт:** ADR-001 запрещает «отдельный vector DB-сервис, очереди,
model router, новый API-слой», а бриф в списке отклонённых подходов прямо
называет «внешний rerank-сервис (ADR-001)»
(`docs/design/2026-09-27-matching-implementation-brief.md:509`). Значит Cohere
Rerank / Jina v2 / Voyage rerank как «API-вариант» решением владельца не
выбираются: это второй внешний сервис. Внутри ADR-001 «API» = уже одобренный
транспорт OpenAI (`src/server/ai/openai-transport.ts`, AI-002, 2026-09-25).

**Но у OpenAI нет rerank-эндпоинта.** Cross-encoder'а (модель, которая читает пару
«запрос+документ» целиком) у OpenAI в API нет: есть эмбеддинги (bi-encoder — уже
закрыто локальной моделью B1) и генеративные модели. Значит «формула B3» меняется
по существу:

| Как в плане (§B3) | Как получается с выбранным транспортом |
|---|---|
| Cross-encoder реранк топ-50 (`bge-reranker-v2-m3` локально или API) | **LLM-скоринг по рубрике** со structured output — это метод 7 из research, то есть механика фазы C |
| Скор пары «профиль ↔ вакансия» из cross-attention | Скор-суждение модели по критериям, с валидацией схемы и grounding'ом на извлечённых полях |
| Локальная модель, ноль передачи текста | Текст вакансии **и текст профиля** уходят провайдеру |

Это не придирка к формулировке: у двух механизмов разные свойства — cross-encoder
даёт детерминированный скор пары и не «объясняет», LLM даёт рубрику, объяснение и
риск нестабильности вывода. Плюс LLM-путь требует temperature=0, валидации схемы
и (по research) отдельного контроля — этого в B3-плане не было, потому что план
предполагал cross-encoder.

**Практический вывод:** «B3 через OpenAI» — это задача фазы C по механикам и
воротам. Она не может идти раньше C0: C0 — предусловие фазы C, и оно же чинит
существующий путь (§4).

## 3. Цена: арифметика по проверенным ценам

Цены провайдера — проверенные 2026-09-25 (`src/server/ai/provider.ts`):
`gpt-6-luna`, input **$0.10/MTok**, output **$0.50/MTok**. Потолки: операция
**1 цент**, квота пользователя **50 центов/месяц**, бюджет среды **$10**.

Размеры наши, из замера решения №2: посты 4.5–6.6k символов ≈ **1.2–1.7k токенов**;
профиль B1 ≈ 0.2–0.3k токенов с рубрикой.

Один скоринг выдачи (топ-50 кандидатов одним запросом — вариант, который влезает
в потолок операции):

| Статья | Токены | Цена |
|---|---|---|
| Вход: 50 × 1.2–1.7k пост + профиль и рубрика | 60–86k | $0.0060–0.0086 |
| Выход: 50 × ~30 (скор + короткое объяснение) | 1.5k | $0.00075 |
| **Итого за выдачу** | | **≈ $0.0068–0.0094 (0.7–0.94 цента)** |

Следствия, которые надо увидеть до решения о включении:

* **Потолок операции 1 цент** съедается почти целиком: выдача проходит «в притирку»,
  и любое удлинение (топ-100, рост описаний, рубрика побольше) его пробивает.
* **Квота пользователя 50 центов/месяц** превращается в **≈ 53–72 скорированных
  выдачи на пользователя в месяц**. Двадцать перезагрузок страницы в день — и
  квота кончится за три дня. Для реранка в продукте квоту надо пересматривать —
  это отдельное решение владельца, а не деталь реализации.
* **50 отдельных вызовов вместо одного** дают те же токены, но 50 операций со
  своими счётчиками попыток и латентность из 50 сетевых раунд-трипов; один
  большой запрос дешевле и по квоте, и по времени.
* **Выделенный rerank-API дешевле примерно в 3.5–4.7 раза** (порядок $2/1000
  поисков ≈ $0.002 за выдачу из 50) и даёт ~250 выдач на 50 центов. Но это ровно
  «внешний rerank-сервис», отклонённый ADR-001: цена следования ADR — примерно
  вчетверо больше за выдачу и вчетверо плотнее квота. Названо, чтобы выбор был
  осознанным, а не выглядел как «API дешевле вообще».

## 4. Предусловия до первого реального токена (проверено в коде 2026-10-01)

Ни одно из этого не выполнено; вместе они означают, что B3-API сегодня не может
сделать ни одного вызова. **Уточнение от 2026-10-01 (аудит существующего
функционала, `docs/OPEN_GAPS.md` A1–A7):** существующий AI-путь при этом уже
*mожет* тратить деньги — в окружении есть `OPENAI_API_KEY`, а `LIVE_AI_ENABLED=false`
ничего не выключает, потому что живой путь зависит от наличия транспорта, а не от
флага; purpose `job_matching` не одобрен, но исполняется; батч-путь идёт мимо шлюза;
резерв меньше запрашиваемого максимума токенов. Это не предусловие B3, а открытый
дефект существующего функционала — см. раздел A инвентаря.

1. **C0, часть 1 — ремонт существующего пути** (решение владельца №10 предписало
   его досрочно; он не сделан). Проверено по коду:
   * шлюз `executeGuardedOperation` (`src/server/ai/gateway.ts:31`) **не проверяет
     whitelist purposes** — у функции вообще нет параметра purpose;
     `isPurposeApproved` (`provider.ts:47`) не вызывается нигде, кроме тестов;
   * `src/server/ai/openai-batch.ts` тянет SDK напрямую (`import OpenAI from
     "openai"`, свой клиент на строке 10) и `executeGuardedOperation` не вызывает
     вовсе — то есть батч-путь идёт к провайдеру мимо бюджета, счётчиков и deadline;
   * mapping `custom_id → snapshot_id` и идемпотентность — из исходного списка C0,
     не перепроверял детально, потому что первые два пункта уже блокируют.
2. **Новый task_type/purpose.** Сегодня `TaskType = "job_extraction" |
   "cv_extraction" | "cover_letter" | "job_matching"` (`src/server/ai/spending.ts:20`),
   а в БД стоит CHECK по тому же списку (миграция 0011). Нужен новый тип
   (`rerank`), миграция, значение в whitelist `approvedPurposes` и решение
   владельца по каждому пункту отдельно — как это делалось для `cover_letter`.
3. **Права источников.** `send_to_ai_provider` — `denied` у **всех трёх** источников
   (`src/server/source-policies.ts:34,92,152`). Без гранта текст вакансии
   отправлять нельзя, то есть реранчить нечего. Это три отдельных решения
   (fixtures, himalayas, jobicy), и они не выводятся из `process_with_ml`.
4. **Приватность профиля — открытый подвопрос, который решение не закрывает.**
   Скоринг по рубрике требует **обеих** сторон: текст профиля кандидата уходит
   провайдеру. Решение №2 (§6.5) выбирало локальную модель именно чтобы этого не
   происходило, и запрещало смешивать версии/логировать текст. Значит нужен явный
   ответ: допускаем ли мы передачу профиля третьей стороне ради реранка — или
   реранк работает только по вакансии и грубым признакам профиля (тогда качество
   суждения ниже и это надо измерить, а не обещать).
5. **Квота и потолок операции** (§3) — пересмотр отдельным решением.

## 5. Латентность: решение владельца и уточнение

Решение: «добавляем предупреждение и поднимаем бюджет до тех пор, пока не
появится более мощный GPU».

**Уточнение по существу.** Обоснование «до появления GPU» относится к **локальному**
реранкеру: там узкое место — наша CPU (измерено на соседней модели: ~0.7 с на один
живой пост за проход, а cross-encoder считает пары — топ-50 выходит в десятки
секунд). У выбранного **API-варианта** наша CPU не участвует: время определяет
провайдер (один запрос с ~60–86k входных токенов), и GPU его не ускорит. То есть
поднимать бюджет «до GPU» смысла не имеет — имеет смысл отдельный бюджет **стадии**
с предупреждением, а железо тут ни при чём.

**Форма, которую предлагается принять (и почему она ещё не в коде):**
* бюджет `p95 ≤ 250 мс` (`src/domain/rank-guardrails.ts:31`) остаётся **жёстким** и
  неизменным: он измеряет нашу детерминированную часть, и ослаблять существующий
  тест нельзя (AGENTS.md: не ослаблять проверки ради зелёного).
* у стадии провайдера — **своя** граница: превышение даёт **предупреждение**
  (`warnings` в отчёте guardrails), а не провал, с записанной причиной.
* механизм (`warnings` + soft-порог) **не добавляется сейчас**: у него нет
  потребителя — стадии не существует, а числа нечем измерить. Спекулятивный код без
  потребителя проект запрещает («не выдавать заглушки за реализацию»). Он войдёт в
  B3 одной задачей, где у него будет измеренный порог.
* как только появится GPU и локальный вариант станет быстрым — вопрос переоткрывается
  на числах, а не на памяти о решении.

## 6. Отложенный вопрос из B2 (записано, чтобы не потерялось)

**Что отложено:** вход реранка. План говорит «реранк топ-50 **после RRF**», но замер
B2 показал, что слияние RRF **хуже** одной BM25 (NDCG@10 0.827 против 0.881), а с
весами дело монотонно: чем меньше вклад dense-ноги, тем лучше. Значит fused-список —
не лучший вход, и «после RRF» держится на плане, а не на измерении.

**Почему откладывать безопасно:** все три варианта входа (одна BM25, fused, порядок
ранкера v4) уже измеримы одной командой `npm run eval:retrieval`; перерешать можно
в любой момент до включения, и это ничего не стоит.

**Цена отсрочки, чтобы она не была невидимой:** если B3 построить на fused-списке по
инерции, он стартует с более слабого списка кандидатов и может «не улучшить NDCG@10»
по причине, к реранкеру не относящейся. Записано здесь как известный риск.

## 7. Что не проверено и не решено

- **Качество реранка не измерено** (нечего измерять: кода нет). Оценка «улучшит
  NDCG@10» — из research, а не из нашего замера.
- **Латентность одного запроса на 60–86k входных токенов у `gpt-6-luna` не
  измерена.** Оценка «секунды» — предположение; до включения нужен один
  пробный вызов (после предусловий §4).
- **Цены выделенных rerank-API** взяты по порядку величины из research и не
  перепроверялись 2026-10-01; в решении они служат только для сравнения порядка.
- **Токенная оценка** опирается на замеры решения №2 (1.2–1.7k токенов на пост) и
  предполагает, что реранк получает описание целиком; если резать по excerpt, цена
  падает, а качество суждения — вопрос замера.
- **Гранты и purpose не выданы**, миграция task_type не сделана, C0-часть-1 не
  отремонтирована.

## 9. Обновление 2026-10-04 (после исполнения предусловий)

**Предусловие §4.1 закрыто:** C0 часть 1 исполнена задачей AI-006 (батч-путь закрыт

**Вопрос §6 (вход реранка) измерен** — `npm run eval:retrieval` на golden-наборе v4
(2026-10-04, словарь v3, референсное время 2026-09-29):

| вход (top-K) | R@5 | R@10 | NDCG@5 | NDCG@10 | MRR |
|---|---|---|---|---|---|
| порядок ранкера v5 (шипнутый) | 0.611 | **0.850** | 0.875 | **0.892** | 1.000 |
| BM25-l1 | 0.595 | 0.734 | 0.765 | 0.810 | 1.000 |
| fused RRF k=60 | 0.590 | 0.755 | 0.735 | 0.771 | 0.833 |
| dense-l1 | 0.575 | 0.823 | 0.707 | 0.766 | 0.806 |

Ответ на отложенный вопрос: **«реранк топ-50 после RRF» не подтверждается** — fused
слабее и BM25, и порядка ранкера по всем метрикам; лучший доступный список кандидатов
на сегодня — порядок самого ранкера. Планировать вход реранка стоит от него, а не от
fused-списка (§6 сам называл этот риск — теперь это числа). Дополнительно: 8 из 38
релевантных постов не попадают в top-10 **ни одной** ноги (complementarity: both 27,
dense-only 2, BM25-only 1, neither 8) — реранкер их не достанет по построению; это
работа для другого ретривера, а не для реранка, и она ограничивает его потолок.

**Открытыми остаются решения владельца (§4.2–4.5) и вопрос разметки §8.2

2. ~~Права источников `send_to_ai_provider`~~ — **закрыто 2026-10-01 (AI-005):
   право выдано всем трём источникам** (`source-policies.ts:38,102,170`). Ранние
   редакции этого пункта и §4.3 называли его denied — это было верно на дату
   доктрины, но перестало быть верным в тот же день. Проверено по коду 2026-10-04.
3. **Приватность профиля** (§4.4): допускаем ли передачу текста профиля третьей
   стороне ради реранка — или реранк работает без профиля (тогда качество суждения
   надо измерить, а не обещать). Остаётся открытым.
4. **Квота и потолок операции** (§3): квота владельца поднята решением 2026-10-01
   до **$1/мес** (в §3 арифметика записана при 50 центах — историческая); при
   $1 это ≈106–147 скорированных выдач на пользователя. Потолок операции
   **1 цент** не менялся и для выдачи топ-50 всё ещё почти весь уходит на неё.
   Решение о пересмотре — отдельное, остаётся открытым.
5. **Разметка кросс-язычного расширения golden-набора** (§8.2) — вопрос открыт.

До этих решений B3 остаётся нереализованным **по построению** (а не по инерции): ни
одного вызова провайдера, ни одной строки кода реранка. Единственное исполненное без
решений — измерение выше (задача
[B3-001](../tasks/B3-001-reranker-input-measurement.md)).
