# B1-002 — устойчивость индексации: недостижимые строки, частичный прогресс

**Результат:** полный индексирующий прогон перестал быть «всё или ничего» и
перестал молча терять работу. Найдена и измерена настоящая причина отказа — не
код B1, а **дефект рабочей БД**: 12 из 700 `job_snapshots.id` недостижимы по
первичному ключу после смены образа БД.

**Триггер:** первый полный прогон (`npm run embeddings:index -- --embedder=local`)
посчитал 493 вектора за ~6 минут и потерял их целиком: одна FK-вставка упала, и
единственная транзакция откатила всё.

**Не входит:** `REINDEX` рабочей БД — это действие владельца (его решение о смене
образа и его данные); задача чинит реакцию кода на дефект, а не дефект.

**Зависимости:** B1-001 (индексация и хранилище), решение владельца №1 (образ БД).

## Что найдено (измерено, не предположение)

| Проверка | Результат |
|---|---|
| `SELECT ... WHERE id = $1` (индексный путь) | 0 строк |
| Последовательный скан той же таблицы с тем же предикатом | 1 строка |
| Аудит всех строк `job_snapshots.id` на достижимость | **12 / 700 недостижимы** |
| `users.id`, `users.email`, `candidate_profiles.id` | 0 недостижимых |
| Тестовая БД (`atlas_starter_test`) | 0 недостижимых |

Все 12 — himalayas, только ASCII, без общих черт во внешнем виде. Причина класса:
btree хранит порядок, вычисленный прежней реализацией коллации (образ
`postgres:17.11-alpine`, musl), а сервер после смены образа на
`pgvector/pgvector:0.8.6-pg17` (Debian, glibc, `en_US.utf8`,
`datcollversion = NULL`) сравнивает иначе — бинарный поиск по такому индексу
даёт ложные «не найдено». Это ровно тот риск, для которого в документе решения
№1 была записана «страховка `REINDEX DATABASE`» при репетиции.

**Следствие для продукта, важнее эмбеддингов:** всё, что ищет вакансию по id
(сохранённые, скрытые, письма, FK-вставки), для этих 12 записей не работает.
Ремедия: `REINDEX TABLE job_snapshots;` (при сомнениях — `REINDEX DATABASE
atlas_starter`), затем повторить `npm run embeddings:index`. Владелец об этом
уведомлён этим отчётом; исполнитель БД не трогал.

## Что изменено в коде

- `src/server/embeddings/embedding-service.ts`: запись по чанкам (25) — своя
  транзакция на чанк и `SAVEPOINT` на строку; FK-нарушение = «строка недостижима»,
  она пропускается и попадает в `report.unreachable`, а не роняет прогон; любая
  другая ошибка по-прежнему прерывает (иначе скрывался бы баг). Новый исход
  `partial_store`. `storeChunk` экспортирован, чтобы это поведение можно было
  тестировать без порчи индекса.
- `scripts/embeddings-index.ts`: печатает недостижимые id и ремедию, exit 1 при
  `partial_store` (нужен человек), частичный прогресс сохранён.
- `docs/EMBEDDING_PLAYBOOK.md`: операционная заметка — что означает
  `partial_store` и что делать.
- Тест: `tests/integration/embeddings.test.ts` — «строка, которую БД не может
  разрешить, пропускается и называется, а не повторяется вечно» (2 хорошие строки
  в том же чанке остаются записанными).

## Протокол V0–V6 (кратко)

- **V3.** `npm run check` → exit 0 (**229/229** unit); `npm run test:db` → exit 0
  (**51/51**, новый тест на пропуск недостижимой строки); `npm run build` → exit 0;
  `npm run test:e2e` → 96 passed. Живой прогон с реальной моделью: 493 вложения
  посчитаны, **481 записан**, 12 названы поимённо — и это ровно те 12 id, что
  нашёл независимый аудит. Итог в БД: **486 векторов** = 498 − 12.
- **V4.** Частичный прогресс: чанк без плохой строки коммитится, плохая строка не
  отменяет соседей (тест); повторный прогон продолжает с места остановки
  (`content_hash`), а не начинает заново.
- **V5.** Существующие проверки не ослаблены: нормальный путь по-прежнему
  `indexed` (integration-тесты не менялись), исключение только для FK-нарушения.

## Циклы ремонта: 1/2

1. Гипотеза (записана `npm run task -- repair` до правки): «коммит по чанкам делает
   частичный прогресс долговечным, а отдельный код отказа с указанием неудачной
   строки отличает дефект базы от ошибки модели». Подтвердилось: живой прогон
   записал 481 вектор из 493 и назвал 12 недостижимых id вместо потери всех 493.

## Ограничения

1. Дефект БД остаётся: 12 вакансий не индексируются и не находятся по id, пока
   владелец не выполнит `REINDEX`. Код лишь перестал из-за них падать.
2. Пропуск строки — не лечение: если REINDEX не сделать, эти 12 записей будут
   выпадать из dense-ноги и из любых id-запросов молча, с записью только в отчёте
   индексации.
3. Прогон по-прежнему последовательный (одна модель, один процесс) — параллельного
   индексирования нет, это осознанно (память модели).
