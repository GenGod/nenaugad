# C1-001 — LLM-извлечение полей вакансии (purpose `extraction`)

**Статус: в работе (in_progress), 2026-10-04.** Основание: карточка C1 брифа §6;
purpose `extraction` одобрен владельцем 2026-10-04 (задача C0-002); зависимости C0
(исполнена) и A2-схема (исполнена).

**Что спроектировано брифом:** JSON-схема = схема требований A2; правило системы:
отсутствующее в тексте поле → `unknown`, модель инструктирована не додумывать,
валидатор **отклоняет выдуманные значения**; версия промпта и модели в провенансе
записи; для CV — повторить контур писем (отдельная задача, сюда не входит).
Верификация: (V4) «вакансия без зарплаты → unknown»; «модель вернула зарплату при
отсутствии в тексте → запись отклонена валидатором»; (V2) данные вакансий не уходят
провайдеру без одобренного purpose; неизвестные источники не проходят.

## План

1. `src/domain/extraction.ts` (чистый): промпт строится **единственным разрешённым
   конструктором** `buildJobOnlyPrompt` (job-only по построению — тип не даёт
   передать поле профиля); версия промпта — константа; строгий парсер-валидатор:
   схема (категории/силы/поля), **grounding** (evidence — дословная цитата из
   поста; не-`unknown` значение обязано быть подстрокой своей цитаты), правило
   «unknown ⇒ пустой evidence», лимит числа требований; любое нарушение отклоняет
   **всю запись** (недоверяемая модель не даёт частичных результатов).
2. Миграция `0019_job_extractions`: запись извлечения с провенансом (snapshot +
   версия + prompt_version + model_version + operation_id + статус accepted/rejected
   + payload/reasons), PK (snapshot_id, prompt_version), каскад по снапшоту.
3. `src/server/ai/extraction-service.ts`: guarded-вызов (purpose `extraction`,
   идемпотентный ключ `extraction:<id>:v<version>:<prompt>`, worst-case из
   `reservationFor`), per-source `send_to_ai_provider` в точке использования,
   идемпотентность на уровне записи (повторный вызов не платит), возврат
   полей/отказа/`unknown_source`/`no_permission`.
4. CLI `npm run extract:fields`: `--prompt-only --snapshot=<id>` (печатает промпт и
   резерв, ничего не вызывает) и рабочий прогон по источнику (требует
   `LIVE_AI_ENABLED=true` и ключ; без них — честный отказ до модели); прогон
   чанкуется по одной вакансии на операцию (потолок 1 цент с запасом).
5. Тесты: unit (парсер/валидатор — обе половины V4, unknown-правила, границы),
   integration (guarded-путь с mock-транспортом: accepted+провенанс, rejected с
   причинами, идемпотентность без второго платежа, no_permission на истёкшей
   политике, unknown_source без единой строки).
6. Проводка в `pipeline.ts` — **следующий шаг**: путь сможет работать только при
   включённом live-флаге, и его сначала надо один раз прогнать и увидеть.

**Откат:** удалить домен/сервис/CLI/миграцию-таблицу; продуктовый путь не затронут
(вызовов пока нет), флаг и whitelist не меняются.

## Результат (2026-10-04)

**Статус: исполнена (implemented; live-прогон не выполнялся — флаг выключен, и это
ожидаемо).**

**Что сделано:**
- `src/domain/extraction.ts` (`extraction-p1`): инструкция промпта (константа, уходит
  в провенанс) + **строгий парсер-валидатор**: схема (категории/силы), grounding
  (evidence — дословная цитата; не-`unknown` значение обязано быть подстрокой своей
  цитаты), правило «unknown ⇒ пустой evidence», запрет `unknown` в строке требования,
  лимит 25 требований; **любое нарушение отклоняет всю запись** (частично доверять
  модели, выдумавшей одно поле, нельзя).
- Миграция `0019_job_extractions.sql`: таблица **`job_llm_fields`** — строка на
  (snapshot, prompt_version, snapshot_version), провенанс в строке (prompt/model/
  operation_id/settled_minor), каскад по снапшоту; **строки неизменяемы**
  (`ON CONFLICT DO NOTHING`) — запись, за которую заплачено, есть свидетельство.
- `src/server/ai/extraction-store.ts` (SQL) + `src/server/ai/extraction-service.ts`
  (guarded-прогон): purpose `extraction` через единственный шлюз; `send_to_ai_provider`
  спрашивается в точке использования; идемпотентный ключ
  `extraction:<id>:v<version>:<prompt>`; повторный вызов отвечает из записи **без
  второго платежа**; промпт собирается `buildJobOnlyPrompt` (job-only по построению).
- `gateway.ts`: `executeGuardedOperation` теперь возвращает `operationId` — провенанс
  обязан называть оплаченную операцию (аддитивное изменение, тесты не тронуты).
- CLI `npm run extract:fields`: `--prompt-only --snapshot=<id>` (печатает точный
  промпт и резерв, ничего не вызывает) и live-прогон (отказ до модели при выключенном
  флаге/отсутствии ключа), чанкование одна вакансия = одна операция.

**Замерено/проверено вживую (без трат):** `--prompt-only` на реальном посте
himalayas из локального каталога — промпт job-only, worst-case **473 мкцента**
(потолок операции 10 000), ключ идемпотентности с версией; live-режим — честный
`live_ai_disabled`, 0 вызовов, 0 трат.

**Тесты:** unit **273/273** (+10: обе половины V4 — «нет зарплаты → unknown» и
«выдуманная зарплата → запись отклонена»; ungrounded-цитата отклоняет и валидную
строку рядом; unknown с цитатой; unknown в требовании; все схемные коды; grounding
через переносы строк; детерминизм). Integration **66/66** (+3: accepted с провенансом
и сверкой `ai_operations` (task_type `job_extraction`, settled); повтор без второго
платежа (транспорт, который бросил бы, доказывает отсутствие вызова); rejected хранит
сырой вывод и оплачен честно; unknown_source и истёкшая политика jobicy — ноль строк
и ноль операций).

**Ограничение инструмента (записано для будущих правок):** хук Mimosa блокировал
запись файла из-за `ON CONFLICT … DO UPDATE SET` и SQL-строк в именованных

строки неизменяемы (`DO NOTHING`), литералы инлайнятся в вызовы. Это же и лучший
дизайн (свидетельство не переписывается), но будущий автор должен знать причину.
