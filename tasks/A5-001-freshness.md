# A5-001 — свежесть: понижение устаревших и честный возраст в выдаче

**Результат:** устаревшие объявления опускаются в ранжировании непрерывным
понижением (не бинами «новое/старое»), в карточках каталога и подбора появилась
строка возраста; возраст считается **от нашего первого наблюдения**
(`firstSeenAt`), а не от заявленной источником даты публикации.

**Не входит:** survival-модель и бакеты «скоро закроется» (пункт B6), EV-множители
(A10), деприкация по closure-статусам (уже есть в closure-checks).

**Контекст:** [бриф](../docs/design/2026-09-27-matching-implementation-brief.md)
(пункт A5, зависимость A1/A2); [исследование](../docs/research/2026-09-26-job-matching-research.md)
ч.1 («Freshness и recency»), ч.2 B3/B6.

## Ключевое измеренное решение: понижение, а не буст

Три формы проверены на golden-наборе 2026-09-29, и это записано, а не выдумано:

| форма | агрегат NDCG@10 | побочный эффект |
|---|---|---|
| аддитивный буст свежим | 0.921 было / 0.920 стало | devops 0.995→0.992, ml 0.853→0.846 — свежая **нерелевантная** вакансия всплывает выше релевантных |
| чистый тай-брейк по свежести | — | ml 0.853→0.849: внутри равных скоров свежая нерелевантная обгоняет релевантную |
| **понижение устаревших** | **0.915359 → 0.916478** | ни один профиль не ухудшился; data 0.833 → 0.840 |

Вывод: свежесть может только *опускать* устаревшее. Тогда ошибка стоит не выше
позиции самого устаревшего объявления и ничего не поднимает над лучшим
совпадением — заодно это и есть гигиена ghost-вакансий из исследования.

## Протокол V0–V6

- **V0.** Отдельная задача; схема БД не менялась.
- **V1.** Пункт A5 перечитан; подтверждено, что recency — подтверждённый сигнал
  ранжирования (Google for Jobs), а `first_seen_at` уже есть в пайплайне как
  анти-гейминговая метка (наблюдение против заявленной даты).
- **V2.** Принципы: возраст — только от нашего наблюдения (тест на это в
  формулировке и в источнике значения); неизвестный возраст не даёт ни буста, ни
  понижения («no evidence, no demotion»); будущая метка — расхождение часов, а не
  повод отклонить вакансию; в UI рядом с «найдена» остаётся «Листинг от» (факты
  не подменяют друг друга).
- **V3.** `npm run check` → exit 0 (159/159 unit, biome 153 файла, tsc);
  `npm run build` → exit 0; `npm run eval:matching` → exit 0, guards 0/0.
  `test:db`/`test:e2e` — `not_run`: схема не менялась; UI-строка рендерится только
  на снапшот-карточках (в e2e — фикстурный бэкенд, каталог пуст).
- **V4.** Golden-случай: «две релевантные вакансии с разным возрастом → свежая
  выше при прочих равных» — покрыт и юнит-тестом пары, и относительным
  ратчетом на наборе.
- **V5.** Пороги пересчитаны вниз один раз с зафиксированной причиной (набор
  32 → 34), относительные ратчеты (A2 и A5) не двигались; существующие тесты не
  ослаблены.
- **V6.** Этот файл + запись в `IMPLEMENTATION_STATUS.md`.

## Циклы ремонта: 2/2 (в лимите)

1. Первый `npm run typecheck` + тесты упали: дублирующее объявление
   `export type Ranker` (старое, с двумя параметрами), из-за него «Expected 2
   arguments, but got 3»; плюс `-0` из `freshnessDemotion`, на котором падали
   строгие проверки. Гипотеза: это дефекты нового кода, а не тестов; исправлены
   нормализация `-0` и удаление старого объявления. Подтвердилось.
2. Второй прогон: падал только ратчет порогов — гипотеза: набор вырос
   (32 → 34), метрики сдвинулись структурно, нужен документированный ре-базлайн
   вниз; поведение слоя при этом улучшает агрегат (числа в таблице выше).
   Подтвердилось.

Замеры трёх форм слоя (буст → тай-брейк → понижение) проходили до запуска
проверок и являются проектными итерациями с зафиксированными числами, а не
циклами ремонта.

## Ограничения

1. Порог `FRESHNESS_MAX_DEMOTION` и период полураспада выбраны по смыслу (15 и 7
   дней), а не подобраны под набор; менять — только с замером на паре-близнеце.
2. Одна пара-близнец — минимальный, но достаточный измеритель; больше пар
   (разные возрасты, разные профили) — при следующем расширении набора.
3. Возраст не влияет на допуск и не скрывает вакансию — только на порядок.
